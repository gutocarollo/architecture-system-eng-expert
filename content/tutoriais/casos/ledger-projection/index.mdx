# Experimente: o saldo precisa explicar sua história

Continue o mesmo caso: [volte ao caso](/jornadas/ledger-projection/); [entenda o mecanismo](/explicacoes/casos/ledger-projection/); [resolva a tarefa](/guias/casos/ledger-projection/); [consulte contratos e fontes](/referencia/casos/ledger-projection/).

Você concluirá uma experiência local e previsível. Você aprenderá a distinguir o fato registrado, a projeção para consulta e a recuperação local de uma transação incompleta. Este é um caso financeiro hipotético com participantes e dados fictícios. Uma corretora de maior porte, do setor em que atua a XP, é apenas o contexto de negócio. O texto não descreve um incidente nem uma arquitetura interna real da XP. A busca delimitada localizou candidatos da nossa stack, mas não estabeleceu um caso histórico completo para todos os conceitos desta família.

## 1. Prepare o ambiente isolado

Abra um terminal na raiz deste repositório de estudo. Confira Python 3.11 ou posterior. Para o caso de data, você também precisa de Node 20.9 ou posterior. Execute `npm ci --prefix labs/architecture` para instalar a versão do TypeScript fixada no lock dos laboratórios. O recibo desta autoria usou Python 3.14.8 e Node v26.8.1.

```sh
pwd
python3 --version
```

O diretório precisa conter `labs/architecture`. Prepare os laboratórios com o comando abaixo. Ele cria uma virtualenv local e instala o SDK OpenTelemetry fixado pelo lock; o caso de mTLS usa a CLI OpenSSL 3.x. Confira `openssl version`; o recibo desta versão usou OpenSSL 3.6.5.

```sh
python3 labs/architecture/setup_labs.py
```

Os programas trabalham em memória ou em uma pasta temporária criada pelo Python. Eles usam somente identidades e chaves sintéticas. A instalação baixa os pacotes do lock. As práticas não fazem requisições externas nem gravam nos sistemas de produção; mTLS usa pares de sockets locais sem abrir porta de escuta.

## 2. Reconheça a entrada que será repetida

Eventos credit/1000, credit/100 e debit/200; snapshot no evento 2; tabela SQLite temporária com 100.000 centavos. Você repetirá a mesma entrada entre as condições comparadas; os eventos e relógios controlados eliminam a necessidade de acertar um intervalo manualmente.

## 3. Execute as duas condições

```sh
python3 labs/architecture/financial.py ledger-projection
```

O programa executa a condição anterior, executa a posterior e termina com `comparison=PASS` quando suas verificações passam. PASS neste roteiro significa que a falha ou diferença esperada apareceu antes e a garantia delimitada apareceu depois. A condição anterior deve mostrar o problema; portanto, observar seu sintoma é parte do resultado correto do exercício.

## 5. Examine a mudança

Abra `labs/architecture/financial.py` e procure a função `ledger_projection`. Localize a decisão que calcula before e a que calcula after. Compare a entrada e o recurso protegido. O modelo anterior e a proteção estão no mesmo arquivo para permitir repetir a comparação com segurança.

Para repetir somente um probe, copie seu nome do campo `probe` e acrescente-o ao comando:

```sh
python3 labs/architecture/financial.py ledger-projection --probe replay-events
```

## 7. Reinicie e conclua

Execute o mesmo comando outra vez. Cada processo começa com fixtures novas; as pastas SQLite temporárias são removidas pelo próprio programa. Não existe comando de limpeza contra banco, cache ou serviço externo.

Os eventos são fictícios. O WAL medido é do SQLite; ele não prova recovery PostgreSQL. Uma outbox, um log de auditoria ou uma projeção sozinha não transforma qualquer sistema em Event Sourcing.
